## 1. Which notable repos exist and what each one actually does (inventory)

### Takeaway
About 35 GitHub repos match "lbp2900" and about 50 match "canon capt". The only widely used Ubuntu installer is **hieplpvip/ubuntu_canon_printer** (209★). Its author is Vietnamese, it is an English translation of the Russian help.ubuntu.ru script v3.3 from 2019, and it has had no commits since 2020-10-02. It and its forks install Canon's proprietary CAPT 2.71 .debs, which are committed into the repos. Those .debs are byte-identical to Canon's, but nothing checks a checksum. The open-source alternative is **captdriver** (agalakhov → mounaiban → ValdikSS and others), with installers that build it from an unpinned git HEAD. Since mid-2026 a wave of small new repos has appeared (brucenguyen1102, sanhos95, suluoniu, ataoua-sudo, gauravyad69, several Vietnamese ones). Each takes a different approach and none is established yet (0–19★).

**What Canon's own .deb needs (this matters when judging every installer's i386 handling)**
- [code] `cndrvcups-capt 2.71-1 amd64` declares only amd64 dependencies: `libatk1.0-0, libc6, libgcc1, libglade2-0 (>= 1:2.5.1), libglib2.0-0, libgtk2.0-0 (>= 2.8.0), libpopt0, libstdc++6, libxml2 (>= 2.6.27), zlib1g, cndrvcups-common (>= 3.21)`. It has **no libpango dependency** and **no :i386 dependency**. — [package in hieplpvip repo](https://github.com/hieplpvip/ubuntu_canon_printer/blob/2084954b00195d8ffbaeb06f3b4d9dd3a0c41430/Packages/cndrvcups-capt_2.71-1_amd64.deb)
- [code] Inside the "64-bit" package, `ccpd`, `ccpdadmin`, `captstatusui`, the `ccp` backend and `pstocapt*` are x86-64 ELF. However `captfilter`, `captdrv`, `captmon`, `captmon2`, all `captmon*` and Canon's libraries (`libcaepcm`, `libcaiowrap`, `libcanon_slim`, `libcaptfilter`, `libColorGear*`) are **32-bit i386** ELF. The LBP2900 PPD (`CNCUPSLBP2900CAPTK.ppd`) sets `*opbidiPlugin: "captmon2"`. `captmon2` needs `libxml2.so.2 libpthread.so.0 libpopt.so.0 libdl.so.2 libc.so.6` and `captfilter` needs `libpopt.so.0 libc.so.6` (from `readelf -d`). So for an LBP2900 the 32-bit set actually needed is `libc6:i386 libpopt0:i386 libxml2:i386` (which pulls in `libicu74:i386`, `liblzma5:i386` and `zlib1g:i386`), plus `libstdc++6:i386`/`libgcc-s1:i386` only for the `captmoncnab*`/ColorGear binaries used by other models. **No binary in the package needs GTK, ATK, Cairo or Pango for i386**, because `captstatusui` is 64-bit. — same package, extracted with `dpkg-deb -x`
- [code] Canon's `/etc/init.d/ccpd` has **no LSB header** and blocks in `while [ \`ps awx | grep cupsd | grep -v grep | wc -l\` -eq 0 ]; do sleep 3; done` until a cupsd process exists. `postinst` creates `/var/captmon` but has the `/var/ccpd` FIFO creation commented out, and it runs neither `update-rc.d` nor `systemctl daemon-reload`. `/etc/ccpd.conf` sets `UI_Port 59787` and `PDATA_Port 59687`. Conffiles are `/etc/init.d/ccpd` and `/etc/ccpd.conf`. — control archive (`dpkg-deb -e`) of the same package
- [code] Canon's `preinst` and `prerm` both run `kill -9 \`ps awx | grep -e ccpd -e captmon | grep -v grep | cut -c 1-5\`` in a `while` loop until nothing matches. [local] On noble, `kernel.pid_max` is 4194304 and `ps awx` prints a 7-character PID column (for example `3837182`), so `cut -c 1-5` returns a truncated or wrong PID. — same control archive; host check against [procps](https://packages.ubuntu.com/noble/procps)

**hieplpvip/ubuntu_canon_printer (the de facto standard)** [code], file [canon_lbp_setup.sh @2084954](https://github.com/hieplpvip/ubuntu_canon_printer/blob/2084954b00195d8ffbaeb06f3b4d9dd3a0c41430/canon_lbp_setup.sh)
- Header: `#Version 3.3 updated on September 13, 2019 / #http://help.ubuntu.ru/wiki/canon_capt / #http://forum.ubuntu.ru/index.php?topic=189049.0 / #Translated into English and modified by @hieplpvip`. It supports 35 models.
- Install path: README says `wget https://github.com/hieplpvip/canon_printer/raw/master/canon_lbp_setup.sh; chmod +x; ./canon_lbp_setup.sh`. The script elevates itself (`[ $USER != 'root' ] && exec sudo "$0"`, line 11). It downloads the .debs with `sudo -u $LOGIN_USER wget` (no checksum). It then runs `apt-get -y update` and `apt-get -y install libglade2-0 libcanberra-gtk-module`, followed by `dpkg -i` of common and then capt. — [README](https://github.com/hieplpvip/ubuntu_canon_printer/blob/2084954b00195d8ffbaeb06f3b4d9dd3a0c41430/README.md)
- amd64 handling: `apt-get -y install libatk1.0-0:i386 libcairo2:i386 libgtk2.0-0:i386 libpango1.0-0:i386 libstdc++6:i386 libpopt0:i386 libxml2:i386 libc6:i386` (line 270). It **never runs `dpkg --add-architecture i386`**. PRs #21 and #30 add that.
- ccpd: it **overwrites `/etc/init.d/ccpd`** with its own version that has an LSB header (lines 198–261, no backup). It runs `service ccpd restart` (line 296) and only afterwards `update-rc.d ccpd defaults` (line 299). On Upstart systems it writes `/etc/init/ccpd-start.conf` instead. Its `restart)` branch loops forever (`while true … ccpd_stop; ccpd_start … [ -n "$1" -a -n "$2" ] && exit 0`) until two ccpd PIDs exist.
- AppArmor: `apt-get -y install apparmor-utils` followed by `aa-complain /usr/sbin/cupsd` (lines 263–265).
- Queue: `lpadmin -p $NAME -P /usr/share/cups/model/CNCUPSLBP2900CAPTK.ppd -v ccp://localhost:59687 -E`, then `lpadmin -d`, then `ccpdadmin -p NAME -o /dev/canonLBP2900`.
- udev: it writes `/etc/udev/rules.d/85-canon-capt.rules` with `KERNEL=="lp[0-9]*", SUBSYSTEMS=="usb", ATTRS{serial}==<serial>, SYMLINK+="canonLBP2900"`. This gives a stable symlink by serial and relies on usblp's `/dev/usb/lp*`. There is no usblp blacklist handling.
- captstatusui: it writes `${XDG_DESKTOP_DIR}/LBP2900.desktop` (`chmod 775`) and starts `captstatusui -P` in the background. `XDG_DESKTOP_DIR` is read from `~/.config/user-dirs.dirs`, and because the script runs under sudo that is root's home.
- Uninstall: `ccpdadmin -x`, `lpadmin -x`, `dpkg --purge` of both packages, then **`apt-get -y autoremove`** (line 119). It also removes the udev rule, the desktop file and `/usr/bin/autoshutdowntool`.
- `canon_restart.sh` runs `service ccpd stop` and `service cups restart`, then waits in `while true` for two ccpd PIDs. It never starts ccpd. — [canon_restart.sh](https://github.com/hieplpvip/ubuntu_canon_printer/blob/2084954b00195d8ffbaeb06f3b4d9dd3a0c41430/canon_restart.sh), matching [issue #19 (2023-09-20)](https://github.com/hieplpvip/ubuntu_canon_printer/issues/19)
- Maintenance: 14 open issues and 6 open PRs (#17, #18, #21, #25, #29, #30). The last merged PR is #4 (2020-10-02). — [issue list via API](https://api.github.com/repos/hieplpvip/ubuntu_canon_printer/issues?state=all&per_page=100)

### Inferences
- On noble amd64, the hieplpvip script **as published** fails at line 270 because `libpango1.0-0:i386` does not exist. It also fails earlier if i386 multiarch is not enabled. With the one-character pango rename and i386 enabled, everything else it needs exists on noble (`libglade2-0` and `libcanberra-gtk-module` are in universe). That explains the run of "works after renaming pango" reports in section 3. On 24.10, 25.10 and 26.04 it breaks again (canberra, glade, libxml2).
- The GTK/ATK/Cairo/Pango `:i386` packages installed by hieplpvip and its forks are unnecessary: no 32-bit binary in the package links them. They are the source of most dependency breakage (pango rename, the gtk2 `adwaita-icon-theme:i386` conflict in issue #13). For an LBP2900 the minimal i386 set is `libc6 libpopt0 libxml2` (+ `libstdc++6 libgcc-s1` to be safe). This comes from my ELF analysis. tutaecos-vn and ethicalvulnlab independently converged on the same small set.
- The order in hieplpvip's script (`service ccpd restart` before `update-rc.d`, with no `systemctl daemon-reload`, and a Canon postinst that registers nothing) explains the widely reported "Unit ccpd.service not found" on 22.04. Its `restart)` loop waits for **two** ccpd processes. Per ataoua-sudo's code comment, ccpd stays at one process when the 32-bit `captmon2` cannot load `libxml2.so.2`. So on a system missing `libxml2:i386`, `service ccpd restart` with hieplpvip's init script would probably spin forever (an inference that combines two code facts).
- No installer pins and verifies Canon's .debs. Since the committed copies are byte-identical to Canon's, CaramOS can pin the SHA-256 values above and either fetch from Canon at install time or reuse a verified local copy. The licensing question belongs to the official-driver research.
- The youngest projects (sanhos95, suluoniu, ataoua-sudo, ValdikSS, brucenguyen1102) contain the best ideas. Each has 0–19 stars and a few weeks of history, and two (ValdikSS, brucenguyen1102) say they are largely AI-written. Treat them as sources of techniques, not as dependencies.

## 2. Code review: problematic lines (security, safety, maintainability) and what CaramOS should reuse or avoid

### Takeaway
Every popular installer weakens system security or reliability in some way. Common patterns: putting cupsd's AppArmor profile in complain mode, overwriting package-owned files without telling dpkg (`/etc/init.d/ccpd`, `/usr/lib/cups/backend/usb`), unverified downloads (some over plain http and then `dpkg -i`, some via `curl | bash`), `--force-all` dpkg fallbacks, unattended `apt-get -y autoremove`, and global changes that affect all printers (masking ipp-usb, blacklisting usblp, permanent `LogLevel debug`, CUPS opened to the LAN or to any address). Canon's own maintainer scripts contain a `kill -9` loop that misparses 7-digit PIDs on noble. A few projects show the right way: sanhos95 packaging, ataoua-sudo's signed-by APT fetch with dpkg-divert, digital-enterprise's pinned release build, and brucenguyen1102's backups with rollback.

### Inferences
**What CaramOS could reuse or do better (synthesis, not tested):**
- **Do not ship or recommend any existing script as is.** Every Canon-driver script found either fails on noble (hieplpvip upstream) or weakens AppArmor, forces dpkg, or uses unverified downloads.
- Canon-driver path done properly. Use a CaramOS helper package (for example through the existing OTA, App Center or Driver Check channels) that:
  - pins the two Canon .deb SHA-256 values listed in section 1;
  - enables i386 and installs only `libc6:i386 libpopt0:i386 libxml2:i386 libstdc++6:i386 libgcc-s1:i386`;
  - neutralises Canon's `preinst`/`prerm` kill loop, by repacking with fixed maintainer scripts or by stopping ccpd cleanly before dpkg runs;
  - ships its own differently named systemd unit (`After=`/`Wants=cups.service`) and masks or replaces the SysV path deliberately, instead of overwriting `/etc/init.d/ccpd`;
  - creates the queue with `-P …/CNCUPSLBP2900CAPTK.ppd -v ccp://localhost:59687`;
  - uses a serial-based udev symlink plus `TAG+="systemd", ENV{SYSTEMD_WANTS}` instead of `RUN+=systemctl`;
  - gives an exact AppArmor local override only if a denial is actually seen, never `aa-complain`;
  - uninstalls without `autoremove`.
- Open-source path. sanhos95's .deb design is the right shape for CaramOS. The LBP2900-specific reliability fixes (suluoniu's XSTATUS change, ValdikSS streaming) and the CUPS USB race fix (CUPS ≥ 2.4.17, which noble's 2.4.7 lacks) are separate problems. Overwriting the distro's `usb` backend, as brucenguyen1102 does, would be undone by every CUPS update. A separately named backend (brucenguyen1102's `capt:` idea, or a patched copy installed under another name) is the safer pattern.
- Avoid global side effects: masking ipp-usb, blacklisting usblp, permanent debug logs, `--remote-any`/`Allow all`/`FileDevice Yes`, and Docker images with root passwords. For the very common Vietnamese "share one 2900 in the office" use case (section 4), make sharing an explicit opt-in that is limited to the LAN.

### Gaps
- I did not run any installer, so the runtime claims (the job-5 wedge, streaming fixes, "works on 26.04") are untested here.
- I did not check whether Canon's `preinst` loop actually hangs or kills the wrong process in practice. The PID truncation follows from the code and the ps format, but no user report clearly ties a hang to it. hieplpvip issue #26 (Mint 22.2, hang at "cndrvcups-capt pre-installation script", 2025-09-11) fits, but the cause is unconfirmed.
- I did not verify whether the noble cupsd AppArmor profile blocks Canon's `ccp` backend or 32-bit filters in practice. ataoua-sudo's comment says "on some releases", without evidence.

## 3. What users report (Ubuntu 22.04/24.04, Mint 21/22, Debian 12/13): success, failure, recurring problems and fixes that worked

### Takeaway
On **Ubuntu 24.04 and Mint 22.x**, several users report printing with the Canon 2.71 driver installed through hieplpvip's script or a fork after one fix: renaming `libpango1.0-0:i386` to `libpango-1.0-0:i386` (or dropping it). Many still needed to enable i386 and to restart `ccpd` by hand. On **22.04 and Mint 21.x** the usual problems were "Unit ccpd.service not found", i386 GTK dependency conflicts, and "prints once, then stops after reboot". Reports for 24.10, 25.10 and 26.04 show the Canon path breaking further (canberra, glade, libxml2.so.2 removed), with users moving to captdriver forks. Open-source captdriver users report jobs stuck at "Rendering completed" or "Sending data", light print density and AppArmor denials on Debian 13.

**Recurring problems and the fixes that worked, as reported**

| Problem | Typical symptom | Fix reported to work | Evidence |
|---|---|---|---|
| Renamed or removed packages | apt error on `libpango1.0-0:i386`; `libgtk2.0-0:i386` conflicts; later `libcanberra-gtk-module`, `libglade2-0` and `libxml2` missing | rename to `libpango-1.0-0:i386`, drop GTK :i386, use t64 names; on 25.10/26.04 fetch noble libs or switch to captdriver | #24, #13, #27, #28, A1525400 |
| i386 multiarch not enabled | `Unable to locate package …:i386` | `dpkg --add-architecture i386 && apt update` | [#7 (2021-06-25)](https://github.com/hieplpvip/ubuntu_canon_printer/issues/7), #20/#21 |
| ccpd not started or not registered | "Unit ccpd.service not found", nothing prints after reboot | `systemctl restart ccpd`, LSB header + `update-rc.d`, a native unit | #11, #13, #24, A1525400, Aarish doc |
| Device node changes (lp0 vs lp1) or usblp missing | "Check the DevicePath of /etc/ccpd.conf" | serial-based udev symlink, re-run `ccpdadmin -p … -o /dev/usb/lpN`, `modprobe usblp` | #13 (2022-09-04 comment), [help.ubuntu.ru](https://help.ubuntu.ru/wiki/canon_capt) |
| Stale previous install | "printer still denies to print" | uninstall first, then reinstall | #14, #3 |
| AppArmor (open driver installed in /usr/local) | `apparmor="DENIED" … rastertocapt` | copy the filter into `/usr/lib/cups/filter` (sanhos95). Users mostly used `aa-complain` instead | mounaiban#50, sanhos95 README |
| Wrong auto-selected PPD | stuck at "Sending data to printer" | PPDs with a 1284 Device ID, or re-pick the driver | sanhos95 README |
| Light print density with captdriver | grey text | official Canon driver (density 1–5), or a different dither | mounaiban#33 |

### Inferences
- For CaramOS on noble, the Canon 2.71 route is **known to work for real users** once i386 is enabled, the pango/GTK i386 cruft is dropped and ccpd is started by a proper unit. This is the lowest-risk path for amd64 LBP2900 users today. It will break on a 26.04 base unless libxml2.so.2 (i386) and libglade are supplied.
- The open-source route still has unresolved reliability reports for the LBP2900 specifically (stuck jobs, multi-page problems, density). It probably needs at least the suluoniu/ValdikSS fixes and a CUPS USB race fix before it can be the default on noble. That is a judgement from conflicting, untested claims.
- "Works once, then stops after reboot" is almost always ccpd not starting at boot. A packaged native unit plus a udev or systemd device dependency addresses the most common complaint in every forum.

### Gaps
- No report found mentions **Mint 22.3** or CaramOS by name, and there is no report with an LBP2900B on Debian 12 using the Canon driver.
- Many reports do not say whether the system had i386 enabled before running the script, so the 23.10/24.04 "i386 not enabled" failures cannot be tied to a default-install change.
- The long captdriver threads (#7, #8) were only read in summary. Their individual workarounds were not catalogued.

## 4. Vietnamese guides and forums: methods recommended, how current they are, pitfalls

### Takeaway
The Vietnamese ecosystem centres on **Lê Bảo Hiệp's (hieplpvip) 2018 tinhte.vn post and GitHub script**, which is still what most people point to. Newer Vietnamese material (a 2024 YouTube video with its own 24.04 fork, and 2026 GitHub toolkits) either patches that script for 24.04 or moves to the open-source captdriver, often for **office print-server sharing to Windows PCs**, which is the dominant Vietnamese use case. ### Inferences
- Vietnamese users mostly need **two things**: install the LBP2900 on one machine, and **share it to Windows PCs in an office**. Half of the 2026 Vietnamese repos are print-server or sharing tools. A CaramOS solution that handles local install well and offers a guided, LAN-only "share this printer" option fits the local demand better than any existing guide.
- The 2018 tinhte post and old hieplpvip commands still rank first. A CaramOS-specific Vietnamese guide, or an in-OS tool, would replace guidance that already fails on noble without hand edits.
- Pitfalls specific to Vietnamese guides: instructions that mix 22.04 and 24.04 steps; "plug the USB in only after installing" (TuTaEcos), which interacts with the serial-based udev symlink step in hieplpvip's script that waits for the device; and A5 paper sizes, since Vietnamese offices often print A5 forms (voz report).

### Inferences
- The help.ubuntu.com and Ubuntu Forums links that installers and blog posts cite are now dead ends. Users following old guides will hit 404s or empty pages, which pushes them further toward random GitHub scripts. That strengthens the case for CaramOS shipping its own maintained path and its own Vietnamese documentation.
- hieplpvip's repo (and its forks) is now the only reachable copy of the Russian script lineage (v3.3, 2019). Its claimed support range (12.04–16.04 in the Russian original) never covered 22.04 or 24.04; those only work through community patches.
- The Russian community itself now points newcomers to mounaiban/captdriver (pinned in 2025), and for 26.04 users have moved to captdriver forks. This is the same direction CaramOS will face on its next base.
